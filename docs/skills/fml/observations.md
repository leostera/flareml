# FML observation manual

This page is embedded in the installed `fml` binary. Read `fml skills properties` for temporal quantifiers and `fml skills checks` for setup and bounds. Observation views are **specification-only**: handlers, initializers, setup, input declarations, and effectful helpers cannot inspect them.

## Actor instances: `instances(A)`

`instances(A)` ranges over all `spawn_bound A = N` potential slots from the initial state, not just instances that have already been created. This makes temporal properties meaningful for actors created in later turns. Each slot has:

- `created: Bool` — false before creation; true afterward and monotone;
- `reference: Option<Actor<A>>` — `None` before creation and the stable routing reference afterward;
- `state: Option<State>` — present for stateful actor definitions only; `None` before creation and the latest committed state afterward.

Stateless actor slots have no `state` field. References and creation status never revert. A universally quantified predicate over instances must handle unborn slots, or explicitly guard with `created`:

```fml
property "created workers eventually finish" {
  forall (worker in instances(Worker)) {
    worker.created leads_to worker.state == Some(true)
  }
}
property "creation is possible" {
  reachable (exists (worker in instances(Worker)) { worker.created })
}
```

A `spawn_bound` of zero makes a universal claim over `instances(A)` vacuous. Pair it with a creation/reachability claim when creation itself matters. `instances(A)` is not an allocator and cannot create references. Enumeration of data domains containing `Actor<A>` is rejected rather than fabricating unborn addresses.

## External slots: `inputs(A)`

`inputs(A)` ranges over external slots captured during deterministic `main` setup for instances of A. A slot exists from the initial state even before it is submitted, with:

- `payload: Message` — the captured typed message;
- `target: Actor<A>` — the captured reference to an instance created during setup;
- `submitted: Bool` — true after the optional external send is enqueued;
- `processed: Bool` — true only after that input's target handler commits.

The two flags start false and are monotone. Registration in setup does not enqueue the message; each slot may be submitted at most once and may remain unsubmitted forever. Processing does **not** imply a reply or any generated message finished. For example, `forall (i in inputs(A)) { i.submitted leads_to i.processed }` checks conditional completion under suitable fairness; it does not force submission. A view with no captured inputs can make a universal claim vacuous. Use a reachability property to establish a non-vacuous path.

## Lifetime generated-message view: `messages(A)`

`messages(A)` requires `message_bound = N` in the check. It ranges over N stable potential slots for enqueues targeting all instances of actor definition A. This includes guaranteed sends in setup, messages generated by handlers, and submitted external inputs. Each slot has `sent`, `processed`, `external` flags, plus `payload: Option<Message>` and `target: Option<Actor<A>>`. Before an enqueue allocates it, flags are false and optional fields are `None`. Identical sends get distinct slots; slots never recycle. `m.external` distinguishes environment input from model-generated sends.

```fml
property "generated replies finish" {
  forall (message in messages(Client)) { message.sent leads_to message.processed }
}
property "a generated reply is possible" {
  reachable (exists (message in messages(Client)) { message.sent && !message.external })
}
```

Unused potential slots have `sent == false`; do not infer from a passing conditional property that a send occurred. Add a reachability query or another claim establishing a non-vacuous protocol path. A finite lifetime pool eventually exhausts under unlimited sends, producing `INCONCLUSIVE`, not silent reuse or message loss. `message_bound` is per **actor definition** across all its instances; `mailbox_bound` is per created **address** and limits pending envelopes only.

Replies require an explicit response message and a condition about the recipient's state or a generated-message observation. `input.processed` only records that the input's own callback committed; it is never proof that a reply arrived.
